# Hotel Affiliate Marketing 推荐体系

本体系用于奥利旅行攻略内容中的酒店、住宿和旅行工具推荐。目标是在不破坏攻略可信度、SEO 和 AEO 的前提下，把自然搜索流量中有住宿预订需求的读者，转化为 Trip.com、Hotels.com、Expedia 等合作平台的 affiliate 点击与预订。

## 核心原则

酒店推荐不是广告位，而是旅行决策的一部分。只有当读者在当前页面、当前段落里确实可能产生“住哪里、住哪个区域、靠近哪个车站或景点更方便”的问题时，才加入酒店推荐。

推荐顺序始终是：

1. 用户需求匹配
2. 内容价值
3. Affiliate 转化

不能为了佣金推荐位置差、评分低、体验不稳定的酒店。不能虚构亲测入住。没有实时核验前，优先推荐住宿区域、预算档位和预订平台入口；具体酒店名需要进入 Hotel Database 后再发布。

## 适用页面

适合加入：

- 目的地攻略
- 城市攻略
- 路线攻略
- 交通攻略
- 机场 / 火车站攻略
- 一日游 / 多日游规划文章
- 住宿决策强相关页面

谨慎或不适合加入：

- 产品页
- 功能页
- 包车强转化页
- 接送服务页
- 没有住宿需求的纯信息页
- 加入酒店会稀释主 CTA 的页面

## 合作平台策略

当前优先平台：

- Trip.com：适合中文用户、多币种支付、酒店 / 机票 / 火车一起查询。
- Hotels.com France：适合比较酒店位置、价格和会员权益。
- Expedia France：适合北美、英国、欧洲用户比较酒店、机票、租车和套餐。
- EconomyBookings：用于租车自驾内容，不混入酒店模块。

未来可加入：

- Booking.com
- Agoda

内容层和平台层要分开。先判断“推荐什么住宿区域 / 酒店类型”，再决定使用哪个平台链接。长期应根据点击率、EPC、转化率和佣金表现动态调整平台优先级。

## 推荐密度

普通目的地攻略：3–6 个住宿入口。

住宿专门攻略：8–15 家酒店或住宿区域。

交通 / 机场 / 火车站攻略：2–5 个位置型住宿入口。

路线文章：按路线节点推荐，每个节点 1–3 个入口。

弱住宿意图文章：0–2 个入口，甚至不推荐。

每个推荐模块控制在 2–4 个卡片内。不要一次给用户 10 个选择。

## 推荐类型

优先覆盖：

- 核心城区青旅：适合独行、学生、低预算。
- 高评分二星酒店：适合只要干净、位置好、价格低的用户。
- 高性价比三星酒店：主力转化档位。
- 高性价比四星酒店：适合家庭、情侣、中高预算用户。
- 位置型酒店：靠近火车站、机场、码头、景区入口、核心景点。

推荐理由要写清楚：

- 为什么住这里
- 适合什么人
- 交通或路线有什么优势
- 不适合什么情况

## SEO / AEO 要求

酒店推荐不能让原页面主题漂移。比如“巴黎周边 10 个小镇”不能被写成“巴黎酒店推荐”。住宿内容必须服务于原主题：

> 如果你准备连续几天从巴黎出发看周边小镇，可以优先住在 Saint-Lazare、Gare de Lyon 或 Montparnasse 一带。

AEO 结构优先使用问答式小标题：

- 巴黎周边一日游住哪里方便？
- 去凡尔赛要住一晚吗？
- 去枫丹白露住巴黎还是当地？
- 巴黎周边游酒店怎么选？

Affiliate 链接必须使用：

```html
rel="sponsored nofollow noopener"
```

页面第一次出现 affiliate 推荐时，应加入低调披露：

> 本文可能包含住宿预订链接。价格和可订情况以平台实时显示为准，我会优先按位置、评分、交通便利度和路线匹配来推荐。

当前落地文件：

## 文章住宿推荐匹配规则

以后优化文章时，先判断文章的住宿意图，而不是机械插入酒店链接。

### 1. 住宿意图分级

**强住宿意图：**城市攻略、路线攻略、周边游基地选择、机场 / 火车站衔接、多日游规划、住宿专题。可放 6–10 个推荐入口，或按城市 / 区域分组。

**中住宿意图：**一日游攻略、景点组合攻略、交通攻略。可放 2–5 个推荐入口，重点解释“住哪里更方便”。

**弱住宿意图：**纯景点介绍、历史文化、餐厅、门票、短资讯。最多放 0–2 个入口，通常放在结尾或相关工具区。

**不推荐放：**产品页、包车强转化页、咨询页、服务边界页、会稀释主 CTA 的商业页面。

### 2. 页面语义提取

每次处理文章，先提取：

- 主要目的地：如巴黎、尼斯、马赛、阿维尼翁。
- 出发地 / 住宿基地：如住尼斯玩摩纳哥、住马赛玩普罗旺斯。
- 交通节点：机场、火车站、码头、景区入口。
- 用户类型：家庭、情侣、朋友、独行、带老人孩子、自驾、公共交通。
- 行程节奏：一日游、多日游、换酒店、连住、早出晚归。
- 商业意图：酒店预订、包车咨询、路线定制、工具页跳转。

### 3. 推荐选择逻辑

优先级顺序：

1. 文章语境是否真的需要住宿建议。
2. 住宿区域是否能解决读者的路线问题。
3. 酒店是否满足高评分、位置合理、价格相对清晰、评论数量足够。
4. 是否适合中文游客、家庭或长线旅行者。
5. Affiliate 平台是否可用。

具体酒店不够确定时，先推荐“住宿区域 + 平台查询入口”，不要硬写酒店名。没有核验过的酒店不得写成“推荐入住”。

### 4. 平台优先级

当前首选 Trip.com。原因是中文用户接受度高，也适合酒店、机票、火车和跨国旅行组合查询。

默认顺序：

1. Trip.com
2. Hotels.com France
3. Expedia France
4. Booking / Agoda：未来接入后再加入

租车、自驾和自由行工具类内容可使用 EconomyBookings，但不要放进酒店卡片里。

## Trip.com Affiliate 批量导入建议

Trip.com 作为首选平台时，不建议直接“抓取平台酒店数据”来自动发布。酒店价格、评分、房态、取消政策都会变化，且平台数据使用也可能受条款限制。更稳妥的方式是：**人工筛选 + 深链生成 + 数据库维护 + 半自动插入文章**。

### 推荐工作流

1. 在 Trip.com 搜索目标城市或区域，例如巴黎歌剧院、尼斯市中心、马赛老港。
2. 按位置、评分、评论数量、星级、价格区间、取消政策筛选候选酒店。
3. 对每个候选酒店打开具体酒店页。
4. 使用 CJ Deep Link Generator 或 CJ 后台深链工具生成 affiliate 链接。
5. 将酒店名、城市、区域、适合人群、推荐理由、Trip 链接、核验日期填入 `hotel_database_template.xlsx`。
6. 批量同步到 `_data/hotels.yml`。
7. 文章优化时，只从 `_data/hotels.yml` 中选择 `status: active` 的酒店。

### SubID 命名规则

为了后续知道哪个页面、哪个模块带来点击，Trip / CJ 链接建议加入可追踪 SubID。命名尽量短、稳定、可读：

```text
页面slug_城市_模块位置
```

示例：

```text
paris-nearby-villages_paris_intro
nice-day-trips_nice_hotel-section
marseille-private-routes_marseille_end
```

如果平台允许多个追踪字段，可拆成：

- page：文章 slug
- city：城市
- module：intro / route / transport / end
- type：hotel / area / tool

### 批量导入原则

第一批只做“城市区域池”，不要一次追求几百家酒店。

建议顺序：

1. 巴黎：15–20 条
2. 尼斯：12–15 条
3. 马赛：10–12 条
4. 阿维尼翁、艾克斯、巴塞罗那：各 5–10 条

每个城市优先覆盖：

- 青旅 / 低预算
- 高评分二星
- 高性价比三星
- 高性价比四星
- 靠近火车站、机场、老城、港口或核心景点的住宿

### 自动化边界

可以自动化：

- 从 Excel / CSV 转换到 `_data/hotels.yml`
- 根据文章语义匹配候选酒店
- 生成酒店推荐卡片
- 检查空链接、重复酒店、缺少 last_checked
- 检查 affiliate 链接 rel 属性

不建议自动化：

- 未经核验直接抓平台酒店名发布
- 自动写“最便宜”“评分最高”
- 自动承诺取消政策或实时价格
- 自动声称亲测入住

### 5. 推荐位置

优先位置：

- 首屏答案后：解决“住哪里方便”的核心疑问。
- 路线方案后：对应路线节点推荐住宿基地。
- 交通段落后：机场 / 火车站 / 码头附近住宿。
- 城市分段后：对应城市或区域卡片。
- 结尾工具区：适合低干扰推荐。

避免位置：

- 标题后立刻硬插广告。
- 每个小段落都插酒店，打断阅读。
- 包车 CTA 附近放太多酒店链接，稀释咨询转化。

### 6. 文案风格

酒店推荐要像旅行建议，不像广告。

可以写：

> 如果你准备连续几天从巴黎出发看周边小镇，住在 Saint-Lazare、Gare de Lyon 或 Montparnasse 一带会更省心。白天坐火车出发，晚上回市区吃饭散步，不用每天换酒店。

不要写：

> 点击这里预订巴黎最划算酒店！限时优惠！

不要承诺“最低价”“最便宜”“全网最低”。价格、房态和取消政策以平台实时显示为准。

### 7. 质量检查

每次新增酒店推荐后检查：

- 页面主题是否仍然清楚。
- 推荐是否和当前段落文意匹配。
- 链接是否有 `rel="sponsored nofollow noopener"`。
- 是否只出现一次 affiliate disclosure。
- 是否没有虚构亲测、评分、价格或入住体验。
- 手机端是否不拥挤、不破坏阅读节奏。
- 结尾相关链接是否与正文链接重复过多。

## 第一阶段落地方式

在没有 Hotel Database 前，攻略页先使用“住宿区域 + 平台入口”的轻量模块：

- 不写未经核验的具体酒店名
- 不写实时价格
- 不写“最低价”
- 不写“亲测入住”
- 用 Trip / Hotels / Expedia 的 affiliate 链接作为查询入口
- 后续用 Hotel Database 替换为具体酒店卡片

## 监控指标

每个模块未来需要监控：

- Hotel module impression
- Affiliate click
- Module CTR
- Platform CTR
- EPC
- Conversion
- Revenue / 1000 sessions
- 页面停留时间是否下降
- 原页面主要关键词排名是否受影响

## 模型与 Effort 自动路由规则

酒店 affiliate 工作流需要在保证推荐质量、读者信任和商业转化的前提下控制 token 成本。后续处理酒店推荐、攻略页嵌入、数据整理和页面优化时，默认按任务难度自动选择模型能力与 reasoning effort。

### Low effort：规则型与信息抽取

适用任务：

- 清理 Trip / Hotels / Expedia affiliate URL，去掉日期、人数、价格、筛选条件等不适合长期使用的参数。
- 识别 hotelId、城市、平台、追踪参数、trip_sub1 / trip_sub3。
- 从酒店详情中提取酒店名称、地址、评分、评论数、区域、交通、设施、优缺点。
- 生成 YAML / Markdown 结构化条目。
- 检查标题字数、description 字数、链接是否为空、字段是否缺失。
- 简单分类、打标签、小范围文本润色。

要求：

- 使用轻量模型或低推理模式。
- 输出简洁，优先给可执行结果。
- 不做过度战略分析，不展开无关背景。

### Medium effort：推荐判断与商业表达

适用任务：

- 判断一家酒店是否值得放入推荐体系。
- 判断酒店适合哪类读者、哪篇文章、哪个区域模块。
- 判断酒店推荐是否会稀释包车 / 定制咨询转化。
- 为攻略正文生成自然、克制、有信任感的酒店推荐文案。
- 设计酒店推荐 CTA、区域卡片说明、affiliate disclosure。
- 检查内容是否有 AI 味、广告味或过度承诺。
- 优化站内链接与酒店推荐的插入位置。

要求：

- 使用平衡模型或 medium reasoning。
- 需要说明判断依据，但不要写成长篇报告。
- 所有推荐必须从读者角度出发：位置是否方便、适合什么行程、有什么取舍，而不是单纯为了佣金。

### High effort：体系设计、核心页面与 SEO/AEO

适用任务：

- 设计或重构整套 Hotel Affiliate Marketing 推荐体系。
- 大规模攻略页结构升级、SEO / AEO 策略调整。
- 核心页面改版：首页、/tours、/custom-travel、主题中心页、重要商业落地页。
- 判断内容矩阵、商业化路径、用户信任、搜索意图之间的取舍。
- 分析 affiliate 推荐对包车咨询转化、页面体验和长期 SEO 的影响。
- 复盘 GA4 / GSC / affiliate 数据，并决定继续、调整或停止某类推荐。

要求：

- 使用高能力模型或 high reasoning。
- 综合考虑搜索意图、商业价值、页面信任、内容差异化、长期复利。
- 如果发现任务实际很简单，应主动降级执行，避免无意义消耗 token。

### 自动升级与降级原则

- 如果任务只是 URL 清理、字段提取、格式整理，默认 low effort。
- 如果任务涉及“是否推荐、推荐给谁、放在哪里、怎么写不伤害信任”，自动升级到 medium effort。
- 如果任务涉及整篇文章、核心页面、SEO/AEO 战略、商业模式或转化路径，自动升级到 high effort。
- 如果信息不足，不要直接 high effort 猜测；先列出缺失信息和最小可执行下一步。
- 对用户已经明确建立的流程，例如“我给你原始链接 → 你清理 → 我生成 affiliate 链接 → 你总结入库”，默认用 low 到 medium，不需要每次重新解释体系。
